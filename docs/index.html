Secrets for Kubernetes, stored encrypted in Git

Lose a cluster.
Keep every secret.

Keyfold seals each secret once — to every cluster that needs it and to an offline recovery key. A controller in each cluster turns it into a Secret. Add or replace a cluster without re-encrypting a single value; lose a cluster, a controller or a key, and recover everything from the repository and any one key that's left.

A CRD and a controller. No vault, no external store, no network hop in the decrypt path.

Why Keyfold

No single key, cluster or service to lose

Most ways of putting secrets in Git hang everything on one controller key or one external service. Keyfold wraps each secret's key to several independent recipients instead — and keeps the parts that matter visible in review.

RECOVER

Any one key brings it all back

A controller, an operator and an offline recovery key can each decrypt on their own. Lose any of them — or every cluster — and the repository plus one remaining key recovers everything, offline, with keyfold unseal.

ADD CLUSTER

Grant access without re-encrypting

Adding a cluster rewraps one small key per object. The encrypted values don't change, so the diff is a one-line recipient change — across a whole directory in one command.

NOTHING TO RUN

A CRD and a controller

Ciphertext lives inline in a GitSecret object and arrives like every other manifest — your GitOps tool or kubectl apply. The controller never clones a repository or calls out.

REVIEWABLE

Who can decrypt is in the diff

spec.recipients, their roles and the commit a secret was sealed from are plain fields — and columns in kubectl get gitsecret.

BOUND

Ciphertext only opens where it was sealed

Each value is authenticated against its namespace, object and key. Copied into another object, it fails to decrypt instead of quietly applying there.

HONEST

Loss is cheap. A leak is not.

Multiple recipients make a lost key a routine change. A leaked key still means rotating the secrets it could read — the docs say exactly which step protects what.

The mechanism

How it works

One random content key per secret, encrypting the values; that key wrapped separately to each recipient. Concepts has the whole model on one page.

1

Seal

keyfold seal encrypts each value with a fresh content key (XChaCha20-Poly1305, bound to namespace/name/key) and wraps that key to every recipient in your environment's keyring — public keys only.

2

Commit

The GitSecret manifest holds only ciphertext, the recipient list, and the commit it was sealed from. Git is the source of truth; review it like any other change.

3

Apply

Your GitOps tool or kubectl apply delivers it — no Keyfold-specific integration, no plugin in the sync path.

4

Reconcile

Each cluster's controller unwraps the content key with its own GPG identity and writes the target Secret. Objects not wrapped to it stay untouched — it holds no master key.

Clusters, people and keys over time

Every change is one command — and says what it changes

Only an existing recipient can grant access: a new cluster's public key alone can never add itself.

WhenRun (as an existing recipient)What changes
Add a clusterkeyfold recipients add <fpr> --role controller -f deploy/prod/ --writeThe wrapped key only. No value re-encrypted.
A cluster or its key is lostInstall a new controller identity, then recipients add it and recipients remove the old oneThe wrapped key only.
Someone leavesrecipients remove <fpr>, then keyfold rekeyNew content key; values unchanged.
A key leakedRotate the secret at its source, then printf %s "$NEW" | keyfold set KEY -f db.yamlThe value itself — the only step that protects what was exposed.
No cluster leftkeyfold unseal -f db.yaml with any recipient keyNothing — values printed to stdout.

Security model

What it defends — and what it doesn't

Defended

  • Losing any one key, controller or whole cluster
  • Ciphertext copied into another object or repository
  • Plaintext in logs, events, status or metrics
  • A secret that only one machine could ever decrypt
  • Silently clobbering a Secret Keyfold doesn't own

Not defended — by design

  • History: a leaked key reads every version it was ever a recipient of — rotate the secrets
  • A cluster admin who can already read Secrets
  • A compromised operator workstation
  • Rollback to an older committed version (visible, not prevented)

Nothing in the cluster serves plaintext on request; the controller decrypts only into Secrets. Full analysis: threat model · decision records.

Install

On Kubernetes

Controller + CRD (Helm, OCI) 
# the cluster's own GPG identity — only its private key goes in
kubectl create namespace keyfold-system
kubectl -n keyfold-system create secret generic keyfold-gpg \
  --from-file=private.asc=controller.asc

helm install keyfold oci://ghcr.io/opscalehub/charts/keyfold \
  --version 0.11.0 --namespace keyfold-system \
  --set gpgPrivateKey.existingSecret=keyfold-gpg

Without Kubernetes

Encrypted files in any repository

git keyfold installs git hooks that encrypt matched files on commit and decrypt them on checkout — plaintext in your working tree, ciphertext in history, push blocked if plaintext slips through. Same envelope; its own key per repository, wrapped to each teammate's GPG key.

Five commands 
git keyfold init --key-backend gpg --gpg-recipient <you> --gpg-recipient <teammate>
git add .keyfold.yml .keyfold/key.gpg .gitignore && git commit -m "configure keyfold"
echo "password: hunter2" > secrets/db.yaml
git add secrets/db.yaml && git commit -m "db credentials"   # ciphertext in history
git keyfold adduser <new-teammate>                           # rewrap, no file re-encrypted
